# 新建项目卡顿：定位、修复与恢复

日期：2026-10-08；修复版本：插件与轻量服务 0.1.1。NX 执行器沿用 0.1.0 协议。

## 真实故障与调用关系

点击“新建项目”后，浏览器向 `3080/api/satellite-thermal/service/projects` 发送 POST。DSH 完成登录校验，再由插件代理转发到 `8790/api/projects`。轻量服务创建标准空项目，保存 `project.json`，返回项目 ID 与内容。这一步不调用模型、不运行 CAD，也不调用 NX。

上传几何时，热服务处理 STEP/ZIP、预览和实际接触识别。用户保存物理输入或提交运行后，队列冻结输入，再与 8791 NX 执行器交换工程任务。NX 软件独立于网页和轻量服务运行。

现场直接请求 8790 的健康检查和列表均超过 12 秒未返回；从 WSL 内部请求同样无响应，排除了仅 Windows 转发或网页的问题。进程还在监听，连接在队列里堆积。

两次 Python 调用栈采样均发现 `thermal-import_0` 标记为 `active+gil`，停在 `cadquery/occ_impl/shapes.py:1556 distance`，上游为旧版 `geometry.py:276` 的整实体最短距离计算。导入线程占用一个 CPU 核并持有 GIL，主 HTTP 线程和调度线程无法继续。该导入的预览文件已生成，卡在后续接触识别阶段。后台线程并没有隔离原生库对整个 Python 进程的影响。

网页 fetch 没有截止时间，“新建项目”的 busy 状态一直等不到 finally；每四秒轮询还会累积更多未完成请求。原代理只有 180 秒 socket 空闲超时，缺少独立连接期限。

## 修复

- CadQuery/OpenCascade 导入和示例生成改在独立子进程，HTTP 进程只排队与保存结果。默认 300 秒上限；超时回收该子进程、保留原文件并显示明确错误。后续任务仍能运行。
- 删除冗余的整实体与平面面片最短距离预检查。自动接触仍由真实面共面、相反法向和正的相交面积证明，不按包围盒重叠直接建连接。
- 对交付包明确声明的“设备包络接触须有原始证据”策略，不把包络碰触转成导热关系；网页显示待核查提示。
- 插件连接最长等 5 秒，普通接口响应头最长等 15 秒；导入等长操作保留较长时限，传输中的上传/下载采用无活动期限。
- 前端普通请求及正文读取最多等 20 秒，错误直接显示在新建弹窗并释放按钮。轮询等待上一轮结束再继续；写操作不自动重试，提示先刷新确认是否已保存。

每次几何导入在对应 `imports/g-*/` 留下 `geometry-job.json`、`geometry-result.json`（成功返回时）与 `geometry-worker.log`。服务重启会将先前 importing 状态标为中断，原文件保留。

## 验证与现场恢复

- 服务测试 32 项通过，其中使用原生持 GIL 的阻塞调用验证：计算子进程卡住时，新建、列表和健康检查仍在 1 秒内返回；超时后下一次导入成功。
- 前端测试 10 项通过；插件测试 9 项通过，涵盖连接、正文停滞、流式传输与取消清理。
- 现场同一 63 组件交付 ZIP 在修复代码的隔离验证中约 18.46 秒完成，保留 34,610 个预览三角形及原 STEP SHA-256。它声明的源证据策略使自动接触为零，并显示提示，不能把这理解为工程上不存在导热连接。
- 用户授权后已停止旧的卡死 8790 进程并从源码 service 启动 0.1.1。实际 HTTP 新建约 47 ms、读取 16 ms、列表 94 ms；临时空验证项目已清理，原有项目与五个既有 run 保留。证据：`validation/hang-recovery-service.json`。
- 3080 DSH 仍响应认证请求，8791 NX 执行器正常并存在工程任务，均未中断。插件更新留给用户通过网页执行；没有自动替换已安装插件。

本次没有进行浏览器视觉验收，也没有重新进行 NX 求解验收。恢复后刷新工作台；旧的中断导入需重新提交。
