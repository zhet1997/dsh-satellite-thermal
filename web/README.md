# 热设计工作台前端

React 18 + TypeScript + Vite 的独立界面。业务请求默认访问 `/api`；官方 DSH 插件注入 `window.THERMAL_API_BASE = '/api/satellite-thermal/service'`。来自服务的 `/api/...` 工件地址会转换到同一代理前缀。界面不直接配置 NX 地址或读取服务器路径，也不请求外部字体服务。

## 已实现的操作

- 新建 / 切换项目、明确标识的体验示例；STEP / STP / 几何交付 ZIP 导入，Excel `.xlsx`、CSV / TSV、Word `.docx`、文字型 PDF、JSON 和文字资料整理。
- React Flow 热拓扑，连接筛选、搜索、自由排版；新增 / 修改 / 删除接触热阻、导热与表面辐射关系；编辑空间辐射、外热流和规定温度边界。
- Three.js 读取实际 GLB，按 `componentId` / `faceId` extras 点选组件和表面；拓扑选中连接或边界时，同时高亮相关组件。源 STEP 三角化、体验示例和 NX 实际回读有不同标签。缺少几何时显示等待状态，不用包围盒冒充真实模型。
- 组件材料、功耗、导热率、光学参数、实体 / 壳表达、薄板厚度和温限编辑；选中面可单独设置发射率 / 吸收率。批量厚度修改只作用于壳对象。
- 参数来源标记、问题定位、标准输入 JSON 查看 / 复制 / 下载；自动运行和网格设置。
- 原算法六向外热流曲线、冷热推荐、同一时刻的手动工况、外热流文件导入与手工载荷编辑。手工修改轨道计算结果时，会转为人工工况并移除原计算分量，避免保留过期证据。
- 运行队列 / 取消 / 历史、固定输入快照、NX 实际回读 JSON 与可用 GLB、真实组件温度及温限检查、能量平衡数据、原生工程和结果文件下载。
- 与 DSH 原生对话联动。消息为 `{type:'satellite-thermal:chat', projectId, revision, selection, prompt}`，发送给同源父页面；独立预览时改为复制问题与上下文。

选区、页面切换、图布局只改变浏览器状态。图布局保存到项目独立的 `localStorage`，不会调用计算接口。物理修改整批提交一次 `PATCH`；新增运行由服务统一处理。收到 `409` 时重新载入当前输入并提示用户核对，避免静默覆盖别处修改。轮询不会将较旧版本覆盖到较新输入。

服务无响应时，健康检查最多等待 8 秒，新建、读取、保存和提交运行等普通请求最多等待 20 秒；示例生成、文件导入、文字整理和轨道热流计算最多等待 300 秒。时限覆盖整个响应正文，超时后停止等待并恢复可操作状态。新建失败提示直接显示在新建弹窗中。后台刷新等待上一轮完成后再隔 4 秒启动下一轮，避免服务卡顿时不断堆积请求。超时不代表服务端一定没有完成写入，所以不会自动重发创建或保存请求；恢复连接后先刷新项目确认状态，再决定是否重试。

## 构建与核验

```text
npm install
npm run build
npm test
npm run dev
node validation/api-ui-contract.mjs
```

开发预览将 `/api` 转发给 `127.0.0.1:8790`。生产文件在 `dist/`，由根插件构建流程打包。接口核验脚本使用 `THERMAL_TEST_URL`，默认是真实本地服务 `http://127.0.0.1:8790/api`，创建独立核验项目并在结束时取消它创建的等待任务。

2026-10-07：TypeScript 严格检查与 Vite 生产构建通过。真实 API 核验的 16 项记录见 [`validation/api-ui-contract-result.json`](./validation/api-ui-contract-result.json)，包括：

- 全部 18 个预览面与实际组件 / 面身份一致。
- 壳厚、上下表面约定、面级光学属性与功耗一次保存只创建一次运行；无变化保存不产生运行。
- 清空温限使用显式 `null`，服务正确移除旧限值；接触参数编辑保留实际接触面积和两侧面。
- 冷 / 热推荐与手动指定时刻的六向值采用同一时间；未提前乘光学系数；旧版本轨道请求返回 `409`。
- 后续编辑不改写历史 `inputSnapshot`；导出返回 ZIP；NX 未连接时没有伪造的完成状态或结果。

**浏览器视觉和交互检查尚未完成。** 浏览器工具受到已有站点访问规则拦截；没有使用其他浏览器或截图方法绕过。桌面 / 移动布局已经实现，但不能将代码审查和构建成功等同于实际视觉验收。

上述 16 项接口核验使用的是 NX 执行端未连接时的服务。后续真实 NX 联调结果以项目根目录的验收记录为准；这些接口检查本身不证明实际建模、求解和浏览器温度云图已经验收。若执行端只提供 VTU / CSV，文件可以下载，三维面板不会把它误当 GLB 成功显示。

## NX 温度与能量平衡展示

运行列表和详情显示服务返回的 `caseName`，从而区分同一输入版本的冷 / 热工况。历史工况名称只取该运行或它的固定输入快照，不借用当前已修改的工况。

温度视图使用 `result.meshUrl`、`temperatureRangeK` 和 `temperatureColorMap`。只有有效的开尔文温度范围与 GLB 实际 `COLOR_0` 同时存在，才标为温度云图并显示摄氏温标；缺失任一项时说明原因并标为实际网格。部分网格没有顶点温度颜色时明确标注。界面按执行端的 `linear-rgb` 色带转换为 sRGB 图例，温度网格采用不受灯光影响的材质，选中轮廓不会改变温度颜色。

能量平衡首先展示设备输入功耗、求解器输入热流、流入热沉的热流、收支偏差和相对偏差，保留有符号数值。缺少报告或数值时给出中文说明；零设备功耗工况的相对偏差标为不适用。原始 JSON 保留在折叠的证据区，不将“数据已回读”标为“工程验收通过”。
